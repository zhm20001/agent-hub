- 可核查证据来自本对话、Hub 项目笔记、任务元数据/收尾/handoff、各轮补丁及测试日志。没有完整 token、计费或人工工时数据，不能给出可信的费用、效率倍数或自动化占比。

本次取证时，`markview-ofm-adaptation` 有 26 条项目笔记，事件游标到 43；**43 是项目事件序号，不是 43 条笔记**。9 个任务的进程墙钟时间合计约 102.45 分钟，不包含主调度者、人工等待、后续构建和 CI，也不等于模型思考时间。机器可读快照及证据 SHA-256 见 [证据索引](2026-10-20-markview-ofm-agenthub-evidence.json)。

## 3. 运行环境与可观测性问题

### P01：服务健康不代表能执行目标任务

**事实。** 原服务健康、没有活跃任务，但白名单只有 AgentHub 目录，Markview 在允许范围之外；运行环境也缺少 `ZCODE_CLI_PATH`。真实派发返回 HTTP 400。允许目录之外的拒绝本身是正确保护，问题是任务启动前没有完成环境预检。

**影响。** 已准备的审计不能启动，需要用户授权修改启动环境并重启服务。不能把服务 health OK 当成执行器、工作目录和配置都可用。

**处理。** 用户允许后，确认 running=0，保留原 cwd/runsDir，重启时加入 Markview 根目录和真实 ZCode CLI；后续明确配对内置及个人 provider 配置，没有改密钥/模型，也没有用临时 symlink 绕过白名单。

**余项。** 只证明这次启动环境已修正；没有证据证明这些设置已安装成永久服务配置。应增加执行前目录、CLI、配置存在性及执行能力检查；不应要求平台自行开放目录。

证据：项目笔记 sequence 1/2/3/5；第一轮请求和 `hub-server.log`。[E1]

### P02：我把 stdout 安静误判成任务停滞

**事实。** 首次审计运行约 81 秒就被我取消。Hub 收尾记录是 `cancelled`、`producedOutput=false`、handoff 为 interrupted；当时后查原始 model IO 的项目笔记明确承认模型正在审计。它不是执行器失败，更不是完成后重试。

**影响。** 浪费一次已开展的审计，增加重新启动和恢复上下文成本。责任在我的调度判断，不能甩给 ZCode 或 AgentHub。

**处理。** 用新的稳定请求身份启动第二次审计，保留首张 KILLED 记录。第二轮遇到长模型请求时，改为结合进程、请求起止、真实工具活动和超时观察，没有再次仅凭安静取消。

**余项。** Hub 的机械输出与模型活动不是同一层信息。可以提供“最近 stdout / 最近工具 / outstanding model request”等证据，但仍不能把某个安静时长自动判成卡死。

证据：首张任务 `resolution.json` / `handoff.json`、项目笔记 sequence 5/19。**本次复盘时，首张任务记录的原始 transcriptPath 已不存在**；误杀判断由当时留下的明确自述支持，不能假装现在又独立重放过那份原文。[E1/E3]

### P03：网络重连提示和终态失败需要区别对待

**事实。** 首张 Codex 票先出现 1/5 至 5/5 的 request timed out/reconnecting，随后恢复并执行了真实命令；后来又出现额度耗尽，最终 FAILED。日志出现 5/5 不等于进程已经终止。

**影响。** 如果看到重连提示就另派写入任务，会与恢复后的原进程争写同一仓库。我曾准备有条件停止，但真实命令出现后未执行停止。

**处理与边界。** 等实际终态再回收、续票；没有并发启动第二个仓库写者。平台应保留 transport、provider quota、主动取消和进程结束的原始区别，不能只汇成一句“失败”。

证据：`task-mvew51py-43lk/raw.log`、sequence 26/29。[E3/E4]

### P04：两个执行器先后额度耗尽，换执行器并未保证连续完成

**事实。** ZCode 返回 HTTP 429、业务码 1308，服务提示 17:20:04 重置；用户明确授权 Codex 接手。Codex 之后也返回 usage limit，并提示约 17:14 再试。项目笔记记录在确认 ordinaryUsageAllowed=true 后，17:18 才继续。

**影响。** 实跑产生明显等待；第一次额度失败留下不完整、尚不能编译的实现。用户授权切换路线解决的是执行者选择，不是另一个账户额度问题。

**处理。** 保存部分实现、失败测试和审查意见；停止依赖额度的工作；没有改 provider 绕过限制，没有把预告重置时间当成自动授权，也没有循环重启失败请求。

**余项。** 本轮没有可靠的事前额度预估和预算编排。不能从此推导“额度限制以后都能自动恢复”；恢复依赖可读账户状态、主调度者和桌面接续。

证据：`quota-block.md`、两张 FAILED 票 raw.log，sequence 22/23/25/29。[E4]

### P05：进程退出、handoff、自报成功与验收是四回事

**事实。** 初审自报 parser-correct，主调度者随后仍复现字面 callout 误识别；review02 完成后，又找到 closure03 和 scope04 缺陷。FAILED 的票也可能留下有价值的代码和通过的测试。

**影响。** 如果调度链以 COMPLETED 或 handoff status=success 自动放行，至少这些问题会进入已接受版本。反过来，机械 FAILED 不代表应丢掉所有工作。

**处理。** 使用“回收原文/差异 → 独立反例与测试 → 接受或下一张纠正票”，没有把机械状态当成语义判决。这与 [ADR-0002](../adr/0002-platform-does-not-judge.md) 一致。

**余项。** 需要更清楚地把运行状态、代理自述、审查意见、已验证提交绑定展示；不能靠新增一个未经验证的“成功”布尔值解决。

### P06：批量命令外层退出 0，掩盖过内部检查失败

**事实。** 首张 Codex 票的一次批量验证输出中，`final-changelog 1`，但包裹该循环的 command_execution `exit_code` 为 0；原因是循环打印返回码后没有把失败传播为脚本退出。之后执行者修复 changelog，并在后续批次汇总失败、实际检查全部通过。

**影响。** 只看工具最外层绿色状态会误报“全检查通过”。这是执行脚本和主调度核验的责任，不是 changelog 检查器误报。

**改进。** 每项保存完整日志及退出码；批处理必须聚合非零状态并最终非零退出。主调度者读取逐项结果，而非信任外层 exit0。最终验收使用重新独立运行的日志。[E3/E5]

## 4. 需求、正确性和审查暴露的问题

### P07：需求已经超出“高亮开关”，UI 与文档却停在旧范围

**事实。** 基线已有 callout 和有限 HTML，四语言下拉文案和中英文设置文档仍称“highlight only/仅高亮”，changelog 缺 callout 说明；5 个已提交源文件还存在格式漂移。

**影响与处理。** 用户无法准确知道支持什么；初审后修正文案、文档、changelog，并把已知格式修正独立提交。它们是已有半成品的缺口，不能说是 Hub 新引入的回归。后续隐藏注释获授权时，再更新旧“不支持 %%”边界，不能拿旧文档阻止新授权。[E1]

### P08：阅读器正确，导出却重新退回默认方言

**事实。** `Config::from_settings` 使用默认 LayoutOptions，没把当前有效方言传给阅读器导出。阅读画面中的 callout、highlight、换行/HTML 在 PDF/PNG/watch 中可能不同。

**原因。** 只打通 parser/layout 参数没有打通创建导出任务的入口，缓存和用户设置不是自动贯通的。

**处理。** 在创建导出任务时捕获 effective dialect，补到导出配置；用真实 App → spawn_export → PNG 布局/PDF 文本提取的边界测试验证，CLI 仍明确使用默认 GFM。不能以检查内部 flags 替代用户路径验证。[E1/E2]

### P09：初审遗漏了转义、代码和格式化 callout 标记

**事实。** `callout_header` 先把 inline 扁平化，导致 `> \[!note]`、代码中的 `[!note]` 等与真实标记得到同样文本。初审虽然列出大量通过项，仍漏掉此反例。

**处理。** 主调度独立 probe 发现；收尾票补源码字面检查和红绿回归。Comrak 对转义节点的 sourcepos 还可能从反斜杠之后开始，因此只切节点范围仍不够。

**教训。** “对照官方类型/别名表正确”不能推出语法上下文正确；审查必须覆盖字面与解释后的差别。[E1/E2]

### P10：隐藏注释最初低估了 Markdown 词法与容器语义

早期 ZCode 部分设计暴露了这些独立问题：

1. 逐行 `mask_inline_code` 不能保护合法的跨行反引号代码跨度。
2. 被转义的反引号不应开启代码保护，否则本应隐藏的 SECRET 会泄漏。
3. quote/list 中围栏的生命周期受容器约束；容器结束后不能保持全局 fence 状态，吞掉或暴露后面的内容。
4. 删除初始注释后再次扫描可见文本，会把原本行中的未配对 `%%` 提升成新块注释起点。
5. 隐藏标题、引用定义、脚注、HTML 锚点、图片不能仅在最后画面上遮住；它们必须在语义解析和资源发现之前被排除。

**处理。** 采用解析副本预删注释、借 Comrak 识别保护上下文、所有语义路径使用可见副本、最终只映射一次的方案，并覆盖 snippet、definitions、深度 fallback、增量/前缀路径。不是简单正则替换。[E4/E5]

### P11：一条早期测试要求了不可能成立的源码子串

**事实。** 测试想从原文 `b %%x%% c` 的连续源码范围中直接切出 `b c`；原文没有这个连续子串。

**影响。** 错误的测试可能诱导实现伪造 source、改坏坐标映射，或为了“绿灯”违背原文保留要求。

**处理。** 将语义文本断言与原文端点/UTF-8/CRLF 范围断言分开。源码范围跨过被删注释是允许的，Document.source 必须保持原字节。[E4/E5]

### P12：全局查找 HTML code 标签，产生虚假的保护范围

**事实。** `<code>` 字样出现在真正 Markdown code 或 HTML comment 中时，并不打开活动 HTML code 作用域；早期实现仍把它当成保护起点，导致后续 `%%SECRET%%` 没被隐藏。

**其他缺口。** 精确字符串闭标签查找还漏掉 `</code >` 的合法空白，以及现有 Reader 支持的未闭合 code/pre。

**处理。** 使用活动 AST HTML 上下文、现有 HTML 分类/事件/闭合语义，并补反例。复用成熟 lexer 的上下文比重新做一个全局字符串扫描更可靠。[E5]

### P13：修好假开标签后，假闭标签和递归局部作用域仍未对齐

**事实。** 真正 `<code>` 作用域内，HTML comment 或 Markdown code 中的 `</code>` 字样不能关闭活动作用域。修好后又发现扁平 descendants 栈与 Reader 递归的局部栈不同：

- `*<code>inside* %%SECRET%%`：强调子树中的 open 不能泄漏到父层，SECRET 应隐藏。
- `<code>*inside </code>* %%KEEP%%`：子树中的 close 不能关闭父层继承的 code 样式，KEEP 应保留。

**影响。** 前一轮通过的测试不足以证明完整作用域等价，导致两张追加纠正票。

**处理。** 最终镜像 Reader 的直接子节点递归、局部作用域和继承 code 状态。缺陷边界和撤回项均保存在审查文件，没有删掉返工历史。[E5]

### P14：普通输入也曾平方退化，内存映射过重

**事实。** 早期每个注释反复搜索整段前后缀/保护范围，块注释还反复完整发现保护区。早期偏移表用每个源字节一个 usize，在本机约为 8N 字节表开销，另有字符串/AST。

**测量。** 同机 debug 单次样例，4,000 条同行注释从约 11.84 秒降至 5.93 毫秒；4,000 个普通跨行块注释约从 56.89 秒降至 37.02 毫秒。它们是生成样例的一次前后测量，不是稳定基准或生产 SLA。

**处理。** 缓存行界限、单调游标/有序范围查询、减少无意义 rediscovery，按删除区间存偏移，映射存储变为随删除数量增长。

**未完全解决。** 含 `%%` 的 OFM 文档仍保守禁用增量/前缀快路径，包括全部被保护或未配对的标记。大量结构性候选注释仍可反复全量 rediscovery，极端输入有平方时间边界。最终验收允许这一明确记录的折中，不能写成“性能问题全部消失”。[E5/E6]

### P15：独立审查也有未经确认的反例，不能照单修复

**事实。** review02 跟进文件提出一个 uninterrupted details 假标签场景，后续因 Reader 可能把 backticks 当 HTML 文本而明确撤回为 unconfirmed；只保留经对照确认的 Markdown Code 假闭标签问题。

**处理与教训。** 审查发现必须与实际 Reader/GFM 控制比较。独立 reviewer 并不天然正确，不能把每条推测都升级为实现义务或最终“修复数量”。[E5]

### P16：视觉验证的字体、解析方言和验证目标必须分开

**事实。** 第一轮 PDF 使用测试字体子集曾出现缺符；改用系统字体生成并查看后，13 类 callout 图标、高亮、上下标及展开正文表现正常。主题整理后的 UI smoke 使用命令自身默认方言，只能证明主题能加载、画面可检查。

**影响。** 缺字方框可能被误诊为 OFM 渲染问题；反过来，默认方言的漂亮截图也不能证明 OFM 的语义正确。

**处理。** 保留字体条件、系统字体 PDF 与逐页检查；主题 smoke 不冒充 OFM 行为验收，行为由专门测试支撑。[E1/E7]

### P17：“剩下的都是 Obsidian 仓库/编辑能力”并不准确

**事实。** 截至隐藏注释验收，仍有读取语法差异：callout 富标题、行内脚注、图片尺寸后缀、彩色高亮等；HTML、数学和 Mermaid 也只是各自原生实现的覆盖范围，不是完整 Obsidian 等价。用户随后认可 lite 范围，这不是这些差距已经实现。

**范围随上游变化。** 当时差距矩阵列 wikilinks 未支持；后来 rebase 合入上游已有 wikilinks/文件夹能力，当前不能继续照搬旧表，也不能宣称该能力由本轮新增。“不做 wikilinks”约束的是本轮自研范围，不意味着删除上游功能。[E6/E8]

## 5. 工作区保护、接续和成本问题

### P18：既有脏改动与新修复交织，无法干净地单独暂存

**事实。** 新 callout guard 位于原来未提交的函数内部。即使新差异很小，也不能脱离该函数独立形成有效提交。导出等新提交在当时也依赖工作副本已有 `ofm` 字段，不能被描述成可以任意单独 cherry-pick 的独立功能。

**处理。** 保存原始 patch/hash、parser-only patch、20 文件整体 patch；其余 18 个基线文件逐字节未改。先做完实现与可审阅证据，再询问提交边界，用户允许后才将相关基线与修复合并。没有顺手提交 Hub 中 7 个既有新增票。

**代价与建议。** 这不是完全自动提交；有一次真实的人类范围决策。更理想的是开始时就记录工作副本所有权和依赖，尽早将相关基线单独安置。不能为了提交漂亮而丢掉用户半成品。[E1]

### P19：失败任务可能在归档瞬间仍新增文件

**事实。** ZCode 额度失败前后，首次回滚安全断言因新 module 刚出现而停止；该次断言未执行修改。随后补齐 tracked patch、未跟踪 module 和测试，才反向应用本轮自有改动，恢复已验证基线。

**影响。** 仅凭某次 git diff 归档会漏掉未跟踪文件，或与仍在结束的写入竞态；盲目 reset/clean 会毁掉无关工作。

**处理。** 确认终态、精确核对四个自有路径、保存完整内容和失败证据，只逆转自有且一致的内容。Codex 接手再恢复/重写这份未验收半成品。[E4]

### P20：共享 cwd 的串行写入靠提示和主调度纪律维持

**事实。** 本轮以单写者方式运行，主调度在 worker 活跃时只读审查，待终态后再写修复、验证、提交。现有证据没有显示这轮发生了两个写者互相覆盖。

**局限。** 单写者依赖反复查活跃任务、提示约束和主调度判断，不能把它说成已经证明平台具备仓库级写锁。误杀后立刻重派等场景尤其要求确认原进程实际结束。

**建议。** 可增加同 cwd/仓库运行占用提示、显式所有权和带前置条件的派发；这是改进建议，不是本轮已实现的功能。

### P21：真实长程接续依赖 Codex 桌面 heartbeat，不是 Hub 自己唤醒主脑

**事实。** 约每 5 分钟的 `markview-ofm` heartbeat 负责唤醒本对话；Hub 保存任务、项目笔记和接续材料。用户可见消息中有连续 heartbeat。取证时该 automation 为 PAUSED。

**影响与边界。** 等额度期间没有可行动变化，按既定策略静默，不能把静默全部解释为服务失灵；但整条闭环仍依赖本机、Codex 应用和该对话可运行。Hub 子进程可持续不等于父聊天能自动醒来。不能宣称本次验证了独立于桌面的无人值守调度。

**请求身份。** 同一 request_key 用于幂等取回原任务，不会把 FAILED 偷偷重启；纠正票使用新 key 并关联 ended dependency。后三张 Codex 纠正票保留同一个 native sessionId，因此是“多张串行票、恢复同一模型会话”，不是每票都从全新会话开始。

### P22：上下文重复和验证返工有成本，尚无可量化收益结论

**事实。** 纠正票重复携带原验收、前票 handoff、项目状态和详细约束；同一源树多次完整跑库测试、根测试、fmt、clippy，再由 lead 重跑。它们在发现新缺陷后有验证价值，也消耗时间与上下文。

**不应推断。** 没有 token/计费汇总，不能证明额度耗尽由重复提示造成，不能算出节省了多少人工，也不能将所有测试重跑都归为无效浪费。

**建议。** 保留精确约束和本轮差异，引用稳定证据文件而不是反复复制全部长报告；新变更先跑相关反例，最终接受点再全量验证，并记录实际资源数据。

### P23：接续笔记仍含旧状态、快照冲突和缺失引用

**已确认的三处问题。**

1. 第一轮 acceptance.md 开头和最终核验说已完成提交，但中间“接续事实”仍写旧 HEAD 与 20 文件脏改动。它是追加式更新留下的相互冲突快照。
2. 本次取证时 Hub 最新 sequence 43 仍是 `393c55c8` 全绿；之后的 PR #69 已创建于 `0a597bb2`，却只写在单独 evidence summary 和聊天，未同步回项目笔记。Hub 项目 goal 也仍描述“当前隐藏注释工作”，未完整反映交付后的阶段。
3. 首张 ZCode 任务 transcriptPath 已失效；大量证据起初保存在 `/tmp`，后来复制进 `.swarm-runs`。后者又被 Git ignore，普通 clone 不会获得这些原始证据。证据目录很全不等于它有备份和留存保证。

**影响。** 只看 latestNote、只读文件开头、或只 clone 仓库，都可能得出错误当前状态；本次也必须从默认 20 条 notes 改为取 `limit=100`，才直接看到完整 26 条笔记。`changesSinceVisit` 和原始文件仍需按契约使用，不能把截断摘要当完整历史。

**处理建议。** 为当前状态维护可替换的明确摘要，历史段落标时间/失效；阶段完成时同步项目 goal/note、提交、PR 与验收证据。重要原文需留存策略，本次随证据索引保存了项目笔记快照，但稳定索引和 hash 只能证明核查时内容，不能恢复丢失的文件。本报告不偷偷改写原始事故证据。

## 6. 打包、上游整合和 CI 暴露的问题

这些属于完整交付流程，但不能全归因于 Hub 调度。

### P24：Mermaid 实验分支的样式不符合上游 schema

**事实。** 原 warm-paper-obsidian 样式带实验 `mermaid.aspect_ratio`，上游模板 schema 不支持。用户决定不采用那条实验分支。

**处理。** 保留上游原生 Mermaid，移除实验字段和过时说明，保存暖纸配色/中文合成斜体；将兼容模板提交为 example，并纳入 macOS Resources/styles 与打包验证。旧功能书签先 bundle 备份再 forget，没有把“不用实验”误解成删除上游 Mermaid。

**版本边界。** 本机安装的是 `0.3.0-obsidian-cb3cb70`；后续 rebase/CI/PR 修复并没有在 PR 创建时再替换该 .app。用户手测本机包不等于正在测试 PR 最新 SHA。[E7]

### P25：上游持续变化，旧版本通过不保证新集成通过

**事实。** 首次同步到 `97f6cbe1` 时，解析器、tests、changelog、侧栏/指针等共 7 个路径需要逐提交解决冲突；复杂度检查还要求拆纯谓词/菜单布局、整理比较逻辑，部分有序走访采用有理由豁免。保留双方行为后再独立验证。[E8]

**第二次变化。** 准备 PR 时上游新增 `087fe021` 的按链接 occurrence 悬停修复，又在 4 个路径冲突。合并参数和实现后，隐藏注释还必须将新增 Link.origin 映射回原始字节；否则此前范围映射正确，也不代表新身份字段正确。

**处理。** 补 Markdown link、HTML anchor、wikilink、UTF-8/CRLF 回归，确认无修复时失败、修复后通过；重新测试。首次全量编译还抓到一处 OFM HTML 测试漏传新 origin 参数，Clippy 又要求合并新测试的嵌套 if，均修复后再推送。最终本机 1,434 passed / 9 ignored，严格检查通过；这些途中失败不能删去。[E10]

### P26：我的 jj 检查方式曾造成巨量无效输出

**事实。** 第二次 rebase 尚有冲突时，我直接运行 `git diff --stat upstream/main..Obsidian`；jj 为 Git 导出的冲突树出现 `.jjconflict-*` 合成路径，输出膨胀成约 5,273 个文件、近百万插入的表象。

**影响。** 造成噪声和上下文开销，容易被误认成仓库被批量污染。这不是实际新增了几千个业务文件。该次数值来自本对话工具输出，没有另行保存完整原始日志。

**处理与建议。** 先用 `jj status`、`jj resolve --list` 和有界文件内容处理冲突，确认分支祖先无冲突后才看正常 Git diff。没有据此删除源树、提交冲突投影或推送未解决版本。

### P27：本机全量测试遗漏了 Linux 专用截图门禁

**事实。** `c8a1bea9` 推送后 Linux UI golden 失败：新增三行设置使滚动条滑块变化，14 张预期图未更新。macOS 的 `desktop_goldens()` 返回 false，所以本机测试通过没有运行这组真实截图对比。

**责任。** 我在推送前没有识别平台条件，验证覆盖不完整；不能把它归为 GitHub 偶发失败。

**处理。** 从 Linux CI 取 actual/expected，核对 expected CRC 与本地来源，逐像素确认只在滚动条；更新 14 张基线，容差仍为 2，不关闭测试、不放宽容差。Ubuntu 新运行通过。[E9]

### P28：根 workspace 检查遗漏了独立 fuzz workspace

**事实。** parser 增量 API 增加 Dialect 后，独立 `fuzz` workspace 仍调用两参数 `parse_incremental`，ASAN 构建报 E0061。根 `--workspace --all-targets` 并不涵盖这个独立 workspace。

**处理。** 本机复现红 101，传默认 Dialect 后全部 fuzz bins 编译和 parse target 严格 Clippy 通过；后续 CI ASAN、差分和冒烟通过。

**改进。** API 改动要搜索仓库内调用者，并按 CI 的独立 manifest/feature/平台矩阵核对。不能因为命令里有“all”就称覆盖了整个仓库。[E9]

### P29：macOS runner 容量不足，必须与真实代码失败分开

**事实。** 修复后的 CI 有 macOS job 排队约 15 分钟后被取消，annotation 明确说未获得 hosted runner 并提示 arm64 容量；没有执行到代码测试。

**处理。** 只重跑该 job 一次，取得 runner 后于 2026-10-19 23:32 上海时间完成成功。保留矩阵，不降低测试。旧版本 `393c55c8` 的 run `39274522795` attempt2 最终 success。

**边界。** 这证明该轮 CI 问题已关闭，不代表以后 runner 一定可用，也不代表新 PR 版本自动全绿。[E9]

### P30：已观察到的质量门禁失败，没有在早期验收摘要中充分突出

**事实。** 首张 Codex 票额外运行过复杂度检查，日志已列出 incremental、LayoutOptions 比较及设置 UI 等 5 处超阈值，退出 1；隐藏注释最终验收表列的是当轮测试/fmt/clippy/changelog/diff，不包含复杂度通过。首次上游整合时该门禁再次失败，并增加 comments 作用域走访、worker 比较等项，才做集中整理。

**责任与边界。** 不能把这些全部说成上游更新突然引入，也不能因它不在短验收表内就当作从未观察到。部分来自先前实现，是否属于本票修复范围可以讨论，但已知失败应明确交接，而不是散落在额外日志里。首轮“这些列出的检查通过”不等于“已符合全部上游合入门禁”。

**处理。** 上游整合阶段将相关函数拆分或加理由充分的有序走访豁免，最终完整门禁通过。建议每次验收同时列出必跑门禁、额外观察到的失败、是否为既有债务及谁承接；不应通过删除检查消除红灯。[E8]

## 7. 哪些环节实际起到了作用

这次确实验证了稳定 request_key、持久任务收尾、项目笔记和 handoff 引用能帮助恢复；失败后精确保存/恢复自有 patch 没有丢掉用户基线；串行写入加只读审查避免了本次并发覆盖；独立反例、真实导出边界测试、红绿回归以及最终重跑发现了自报结果之外的问题。停止派发和暂停 heartbeat 也执行了。

但这些成果依赖主调度者持续读证据、判断权限和范围、修正自己的错误、提出反例，以及用户的必要决策。Hub 是运行与记录底座，不能替代验收判断；此次也没有验证其能独立承担主脑、额度预算、工作区锁或跨平台交付。
